# 与 SoftwareCopyright-Skill 衔接

## 依赖与权限

从当前技能目录、已加载技能目录或用户指定位置定位 `software-copyright-materials/SKILL.md`，读取实际内容和版本，不硬编码本机用户名。已有安装即可复用，禁止为使用本技能而静默升级或修改上游。若找不到，仍可开展选题、开发和证据整理；正式材料阶段说明缺少该依赖，按用户授权安装后继续，不伪称已调用。

参考实现基于本机上游 v2.5。它具备项目分析、业务理解、候选代码选择、申请表、手册、截图、确认指纹和 OfficeCLI 输出。本技能补齐前端的产品开发与后端的严格验收，而非复制上游全部脚本。

进入实际生成前读取上游对应参考：`application_fields.md`、`business_understanding_rules.md`、`code_selection_rules.md`、`copyright_material_rules.md`、`manual_structure.md`、`playwright_cli_screenshots.md`、`officecli_backend.md`。按当前阶段读取，并检查脚本 `--help`，不要猜参数。

## 交接顺序

1. **环境与项目。** 在真实项目根目录执行；正式资料放其 `软件著作权申请资料/正式资料/`。用户已明确项目时直接使用。检查 OfficeCLI、Python、需要的浏览器与输出能力，记录已有安装和版本许可；没有可用 Word 后端时只能交付相应草稿。
2. **业务理解。** 将已验收的业务、用户、流程、已实现边界、证据来源映射到上游业务理解结构。每个页面的用途、使用场景、入口、可见控件、动作、限制和反馈都来自实际软件。
3. **登记事实。** 集中确认名称、版本、主体、开发方式、完成日期、发表状态、取得方式和环境。区分开发者与著作权人，工作单位不能代替权属证明。合作协议标题、项目、主体和条款不一致时提出具体差异，由用户决定；不得擅自替换主体或套用旧协议。
4. **代码选择。** 阅读完整源码候选，给出有序文件、选择理由和排除理由。覆盖实际入口、算法及必要数据/状态逻辑，不机械只选前端。根据上游选择规则提交确认；不为凑页数添加重复模块、无关测试或第三方库。
5. **草稿。** 先读取[默认写法与版式](reference-format.md)，确认本次采用默认样式还是用户新给的模板，再生成申请表、代码和用户手册。申请表是登记名称、版本与权属的单一口径；预估页数明确标预估，源程序量统计整个登记软件的实际范围，不能等同于选材行数。新写手册时就按目标结构组织，不能等生成后才发现缺封面、目录、流程图或页脚。
6. **截图。** 沿用本项目已确认方式；没有决定时按上游提供自动或用户截图选择。自动截图运行真实软件；保留截图清单和页面映射，避免只按文件名排序导致错章。用户明确跳过可保留可见占位并标记未完成，不冒充完整图文手册。
7. **正式生成。** 准备整体可审阅草稿并完成上游要求的确认。生成 OfficeCLI Word/TXT，再应用已确定的版式参数，刷新目录页码，之后按[审查与修订](audit-revision.md)核查。上游生成器是后端，不是本技能默认样式已经实现的证明；必要时通过OfficeCLI作版式适配，不修改上游技能。估算、草稿分组和页码文本不作为最终页数依据。

可将多个待确认事实放在一次短问询中，但应先展示具体草稿或差异。不要把“同意继续工作”虚构为用户审阅了尚未出现的所有草稿。用户已经明确要求修订时执行该范围内修订，无需重走整个选题流程。

## 手册的写法

每段围绕实际事务组织：为什么进入此页面、先准备什么、输入/点击哪里、出现什么结果、异常时下一步是什么。自然合并这些信息，不给每章套同一组字段标题。截图旁的文字描述该图真实状态，不把图当装饰。

保留必要的解释，例如“未知状态并非无解”“历史报告反映导出时的复核意见”；将源码实现细节和完整实验数据放在支撑资料。只声明实际实现的功能，不能把 HTML 原型、设计计划和算法构想写成已交付。

用户要求参考文档时，先读取指定的实际DOCX并提取正文及样式证据；旧Markdown可能保留已经删除的附录，不能以它代替最终参考文件。分别提取结构、字体/字号、页眉页脚/目录、表格与图片布局，复用格式而非旧软件业务、截图和登记事实。使用用户明确要求的连续操作叙述和真实界面图注；不用空泛宣传、重复段落或放大的留白凑页数。

**默认不含附录。** 当前用户已将无附录的台账修订版指定为本技能后续格式，正式手册不自动加入“相关文档”、设计/测试文件索引或“详见附录”；支撑资料仍保存在磁盘。用户另行要求时再加入需要的内容，不把有无附录当作法律要求。删除时同步检查目录条目、书签、交叉引用及空白尾页。

## OfficeCLI 的历史兼容经验

上游 v2.5 固定验证 1.0.151；三项目实际经用户许可使用 1.0.157。未来以当前上游要求和用户有效许可为准，不默认降级/升级、不反复询问已有许可。沿用 `OFFICECLI_SKIP_UPDATE=1` 与 `OFFICECLI_NO_AUTO_RESIDENT=1`，显式记录未验证版本选项。

DOCX 写入和包结构修改均由 OfficeCLI 完成。Python 可编排命令、分析 OfficeCLI 导出的 XML、核查源码和组合预览；不要借此绕过后端限制直接写 DOCX 包。Windows 已安装 Word 时，可只读获取真实分页与行数；不要修改用户其他文档或结束其 Word 进程。

技术故障应先缩小为单文件/单页复现，再修复。下列是本机遇到的条件性问题，不是所有版本必然如此：

- `screenshot --grid auto` 可能只有第一页：检查结果，必要时逐个整数页渲染，再组合联系表。
- `refresh` 后旧模板的样式/设置节点可能违反 OpenXML 顺序：在最终 refresh 后校验；必要时通过 OfficeCLI 修复，然后再次检查。不要机械重排所有新文档。
- 多次 Word COM 开关文档可能有对象生命周期问题：只读分页审计可每份文件独立进程执行。
- 页码受旧居中制表位影响时，核对实际右对齐；表后空段落可能挤出空白尾页，不能只看正文 XML 判定没有空白页。

生成后所有修复都应反映在最终哈希与预览中。软件依赖缺失与材料后端缺失是不同问题，互不成为停止全部独立工作的理由。
