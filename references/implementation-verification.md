# 实现、验证和真实证据

## 完整软件的最低含义

从用户实际输入运行到可使用输出，并对主要失败路径给出明确反馈。为当前范围提供启动方式、依赖说明、可重复示例和源代码。不要把静态页面、固定返回值或预先生成的结果当作算法实现。

实现与设计有差异时记录“设计意图—实际行为—原因—影响”，修改用户说明与验收口径。旧设计可以保留历史状态；判断软件现状要结合实际入口、运行结果与最新验收记录。

开发工具、运行依赖、界面版本与登记版本分别核对。允许内部语义版本 1.0.0 与登记 V1.0 建立明确映射；README 仍写 V0.1 或待实现时，应更新当前说明或明确标注历史，不能放任材料和实际界面互相矛盾。

## 先正确，再比较

验收覆盖关键语义，而非复刻实现细节。优先采用可独立判断的期望结果、小规模枚举、全量参照或业务不变量。

| 任务类型 | 有意义的正确性检查 | 容易漏掉的边界 |
| --- | --- | --- |
| 表格匹配 | 一对一约束、候选召回、完整匹配集、人工决定与算法结果分离 | 错误编号、缺失字段、重复名称、歧义候选、大分量降级 |
| 增量检查 | 每次变更后与全量的完整问题、成员、聚合、证据和不可判定状态一致 | 删除、跨组变更、等值原文变化、规则变化、基线不兼容 |
| 约束排班 | 独立核查全部硬条件；小规模枚举验证目标与范围 | 锁定冲突、区域外容量、跨时段、旧版发布、UNKNOWN |

有状态应用按风险测试失败/取消不发布部分结果、版本冲突不能覆盖成功版本、重启恢复状态清楚。导出检查完整记录及其关联，不受页面预览上限截断；表格处理按需要测试前导零、公式文本、金额精度、空值与长文本。

浏览器或桌面验收至少跑通真正关键的一条业务闭环及主要异常路径。真实截图绑定页面、输入、软件版本和运行时间；原型与正式页面分别存放。更换功能或按钮后检查相关截图是否过期。

## 算法实验

先保存原始数据来源、生成方式或脱敏方式、规模、种子、参数、环境及计时范围，再运行比较。基线与改进使用同一问题、相同数据、合理可比的线程/预算/预处理；无法比较的设置明确区分。

将以下指标拆开：正确性/质量；候选对、重算规则或变量数量等工作量；引擎时间与端到端时间；具体定义的内存；成功、不可行、超时未知、取消、跳过及回退比例。

端到端计时写明是否含读取、预处理、基线准备、数据库、复核、导出。未完成的方法没有导出阶段，不能直接与完整方法计算全流程加速比。`tracemalloc` 只反映相应 Python 分配；RSS、峰值采样及原生库内存不能互换名称。

做足以支持当前结论的重复、规模和变化分布，公开中位数/范围及失败。小样本只能支持有限观察，不写统计显著。消融只移除要考察的机制，若同时影响其他机制，应说明混杂。保留负向结果，不能挑最好的一次或只报告最有利规模。

“局部最优”仅针对冻结区域/当前模型；“可行”不是“最优”；UNKNOWN 不是无解；诊断得到足够冲突集合不代表最小冲突集合。若实际求解器语义不同，以其官方文档核对。

## 进入材料阶段的条件

核心承诺已有实现；关键流程与不变量检查通过；失败与边界有明确说明；功能—源码—验证对应表完整；运行与截图可复现。某项试验未完成时可以缩小性能结论，不能把未实现功能降格写成已实现。

进入阶段时冻结代码证据。之后改动算法或业务代码，要复验受影响功能并更新源码材料、截图和对应描述；仅改文档排版则不用重跑全部产品测试。
