# 从真实需求到可实现设计

## 方向选择

先查看用户已提供的行业、可用数据、电脑和时间约束。可只读核查 CPU、内存、磁盘、系统、解释器及已安装工具；未知硬件不要猜。询问实际使用者和反复处理的事务，比泛问“要什么软件”更有用。

必要调研优先使用行业机构、产品官方文档、算法原论文与项目官方文档。使用实时网络验证当前产品/技术信息，记录来源和访问日期。公开登记名称通常只能说明有类似软件；无法取得完整材料时，不能宣称已比较其实现、证明本项目独创或证明某份网络样例已被受理。

给出通常 3—5 个差异明显的候选，数量随请求调整。每个候选写清：

| 项目 | 要回答的问题 |
| --- | --- |
| 使用者与频率 | 谁每周或每月反复遇到什么问题？ |
| 输入与交付物 | 能取得什么合法数据，输出如何被使用？ |
| 当前办法 | 人工、Excel、现成软件或已有算法怎么做，具体卡在哪里？ |
| 改进机制 | 改动候选搜索、状态维护、约束模型或复核决策中的哪一部分？ |
| 验证方法 | 用何种基线、正确性标准和指标判断有帮助？ |
| 实施成本 | 数据、依赖、硬件、时间与不确定性是什么？ |
| 独立产品边界 | 与已有项目在核心输入、算法、状态模型和输出上有何差别？ |

优先选“任务真实、数据可得、闭环可交付、改进可测、资源能承担”的方向。可以给相对评分辅助比较，但不要用任意加权总分代替解释，也不能因名称换了就认定是独立新软件。

没有真实数据可先用合成输入开发与验证机制，明确尚未得到真实业务效果结论。若核心价值必须依赖暂不可得的接口、授权数据或大规模训练，先缩小范围或换方向。

## 算法设计卡

对核心改进形成设计卡，而非先堆算法术语：任务输入输出与硬条件；合理基线；问题出现的分布/规模；新增机制；数据结构与不变量；复杂度与资源成本；回退条件；验收指标；反例和来源。

三种可复用思路是：匹配任务改善候选召回与歧义处理；重复检查利用变化定位和依赖维护；排班任务用稳定身份和局部修复减少无关调整。不能将它们套给不适合的业务，也不能称使用已有求解器本身就是新算法。

## 产品设计与开发准备

将任务写成输入—处理—结果—复核—保存/导出的流程，只有业务需要时才增加历史、备份、任务取消和发布功能。每个页面有明确使用情景、控件、输入限制、结果和失败反馈。

至少明确：数据模型与稳定标识；算法输入输出与不变量；状态与事务边界；异常、取消和恢复行为；文件导入导出范围；主要模块；验收样例。针对有状态应用补充旧版数据、陈旧页面和并发更新的处理。

形成简洁的需求/算法设计及实施计划，不要求每个小项目写固定数量的设计文档。先实现一条可运行的业务纵向流程，再扩展已确认范围。交互原型可辅助理解，但标记为原型，不算软件完成证据。

预先建立“业务功能—实现文件—测试—页面截图—手册章节”对应表，开发中更新。它是以后编写材料的索引，不能用一张空表替代实际实现。
